# MES 权限矩阵与安全边界

## 身份与租户边界

1. 除健康检查外，HTTP API 必须同时提供 Bearer API key 和
   `x-tenant-id`。租户缺失时拒绝请求，不使用默认租户。
2. `x-tenant-id` 必须命中 `MES_ALLOWED_TENANTS`。API key 只证明网关访问，
   不能单独证明用户身份。
3. `x-user-id`、`x-role`、`x-factory-id`、`x-scope`、`x-session-id` 和
   `x-trace-id` 必须由可信身份网关注入。客户端直接伪造这些请求头不能视为
   已完成 SSO/JWT/RBAC。

## 角色矩阵

HTTP 写入边界使用显式 `x-user-role`。健康检查和所有读取方法不要求该头，
以保持现有只读调用兼容；写入或控制方法缺少路由能力标注时直接拒绝。

| 路由能力 | 允许的 `x-user-role` | 典型用途 |
| --- | --- | --- |
| `read` | 无额外角色要求 | 查询、健康检查、Agent 只读工具 |
| `write` | `operator`、`engineer`、`supervisor`、`admin` | 报工、告警处理、事件接入、库存业务写入 |
| `control` | `engineer`、`supervisor`、`admin` | 设备/产线/模拟器控制、策略治理、维修控制 |
| `admin` | `admin` | 租户、工厂、主数据、审计和持久化治理 |

所有非 GET/HEAD/OPTIONS 的 HTTP 路由都必须使用
`RequireCapability('read'|'write'|'control'|'admin')` 明确声明能力；未声明
的变更路由 fail-closed。`x-user-role` 只提供最小权限判定，不替代可信网关
签发的身份和正式 SSO/JWT。

`x-role` 是策略、Agent 和模拟器控制服务沿用的业务角色头。当两个角色头同时
出现时，后端要求它们映射到同一能力角色，否则拒绝请求；兼容映射如下：

| 业务角色头 | 路由能力角色 |
| --- | --- |
| `system_admin`、`admin` | `admin` |
| `plant_manager`、`production_supervisor`、`supervisor` | `supervisor` |
| `equipment_supervisor`、`quality_supervisor`、`engineer` | `engineer` |
| `team_leader`、`auditor`、`viewer` | `viewer` |
| `operator` | `operator` |

只提供 `x-user-role` 时，通用写入路由可完成路由级授权；策略、Agent 和模拟器
控制接口还会按既有业务契约要求 `x-role` 及用户、工厂、范围、会话和 trace
上下文。网关必须负责生成并保持两者一致，不能让调用方自行提升其中一个角色。

| 角色 | 读取业务数据 | 策略仿真 | 审批/撤销 | 仿真执行 | 直接写审计日志 |
| --- | --- | --- | --- | --- | --- |
| `system_admin` | 是 | 是 | 是 | 是 | 是 |
| `plant_manager` | 是 | 是 | 是 | 是 | 是 |
| `production_supervisor` | 是 | 是 | 是 | 是 | 否 |
| `equipment_supervisor` | 是 | 是 | 是 | 否 | 否 |
| `quality_supervisor` | 是 | 是 | 否 | 否 | 否 |
| `team_leader` | 是 | 否 | 否 | 否 | 否 |
| `auditor` | 是 | 否 | 否 | 否 | 否 |
| `operator` | 否 | 否 | 否 | 否 | 否 |

资源读取还必须满足 `factoryId` 和 `scope`；同一租户不等于可以读取该租户
的所有工厂或产线。

模拟器控制接口（启动、停止、暂停、复位、故障注入等）仅允许
`system_admin`、`plant_manager`、`production_supervisor` 和
`equipment_supervisor`，并且在校验身份和权限之前不会发布 MQTT 命令。

## Agent 只读边界

- Agent 工具集合只允许 `AGENT_READ_ONLY_TOOLS` 中的查询工具。
- HTTP Agent 请求必须提供网关身份头；请求体中的 `authorization` 仅用于
  一致性校验，不会覆盖网关身份。
- Agent 不得调用设备控制、产线变更、工单写入、审批决策或策略执行接口。
- Agent 调用会记录租户、用户、会话、trace、工具和脱敏参数。

## 策略审批与执行

1. 每个策略候选固定 `requiresApproval: true`，策略结果固定
   `executionAllowed: false`。
2. 高风险候选必须通过受治理的策略审批接口；不能通过通用审计审批接口
   绕过治理流程。
3. 审批绑定具体 `simulationId:candidateId`，禁止跨仿真复用审批。
4. 创建者不能审批自己的策略；执行必须携带已批准的 `confirmationId`，且
   只能进入仿真执行状态，不得控制真实设备或写入生产状态。
5. 审批创建、决定、撤销和策略生命周期变化都必须产生审计记录。

## 设备 Profile 与协议

设备 Profile 的 `verified=false` 表示模板未获得厂商兼容性验证，不能据此宣称
真实设备可用。协议未实现时必须返回 `unsupported` 并停止启动，不得降级为“已
连接”。

## 当前部署前置条件

- 必须接入真实 JWT/SSO 或可信身份网关，并让网关签发不可伪造的用户、角色、
  工厂和资源范围；静态 API key 不是完整 RBAC。
- 启用 `DATABASE_ENABLED=true`、完成迁移并设置
  `MES_AUDIT_PERSISTENCE_REQUIRED=true`（生产环境同时设置
  `DATABASE_REQUIRED=true`）后，审计事件和审批状态才会在 PostgreSQL 中可靠
  落库；数据库不可用或迁移缺失时启动/请求会 fail-closed。
- 当前仍未完成正式 JWT/SSO、跨实例锁和现场级不可篡改存储验收，不能据此宣称
  已达到完整生产审批系统。
