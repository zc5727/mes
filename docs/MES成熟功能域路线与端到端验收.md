### 3.1 强制权限规则

1. 前端隐藏或 disabled 不是安全边界，NestJS 每次请求必须重新鉴权和校验数据范围。
2. ERPNext、ThingsBoard 和 Gateway 使用独立服务账号，只授予指定接口和主题权限。
3. 策略默认只生成建议，`requiresApproval=true`；未经审批不得执行。
4. 故障注入仅允许 demo/test 环境，不得复用真实设备控制接口。
5. 停线、设备写入、批次锁定/放行、工单跨线和图纸发布必须二次确认、审批和审计。

## 4. M1-M5 路线与退出标准

| 阶段 | 目标 | 必须交付 | 退出标准 |
|---|---|---|---|
| M1 | 四线可控演示 | API/local、故障注入恢复、产线 CRUD、告警高亮 | 故障→告警→看板→恢复通过；四线不串线；关键按钮有结果 |
| M2 | ERPNext 生产底座 | ERPNext 旁路、adapter、ID 映射、业务同步、回退 | 四线影子对账一致；订单/工单/报工幂等；回退演练通过 |
| M3 | 设备与质量 | ThingsBoard/Gateway P0 接入、动态看板、图纸和质量流程 | telemetry/告警可追溯；质量草稿可复核；无静态数据冒充实时 |
| M4 | 策略与治理 | 五类策略、审批、权限、审计 | 未授权拒绝；高风险动作需审批；策略只建议且可追踪 |
| M5 | 桌面试点冻结 | Tauri 编排、安装、升级、清理和回滚 | app/dmg 可重复启动/退出；无残留进程；全量回归通过 |

### 4.1 优先级规则

- **P0：** 数据错、越权、重复报工、状态回退、设备控制绕过审批、服务无法恢复。
- **P1：** 关键流程缺失、实时性降级无提示、质量/追溯不完整、桌面运行体验问题。
- **P2：** 报表增强、布局、高 DPI、性能优化和辅助操作。
- **P3：** MTConnect、EtherNet/IP、复杂 APS、AI 训练、ERP/WMS/PLM 深度集成。

## 5. 端到端验收清单

每项记录环境、版本、执行人、时间和证据路径。`PASS` 必须有 API 响应、日志、测试输出或截图，不能只凭页面存在判断。

### E01：启动与数据来源

- [ ] 启动 ERPNext、ThingsBoard/Gateway、NestJS、模拟器和前端。
- [ ] 页面显示环境、租户、模式、数据来源和连接状态。
- [ ] 后端不可用时显示错误，不回退静态假数据。
- [ ] 关闭并重新启动后端，读模型恢复且无状态回退。

### E02：四条产线生产闭环

- [ ] 四条产线和设备数量与种子一致。
- [ ] 创建订单，生成工单并分配到指定产线。
- [ ] 开工、暂停、恢复、报工、质量判定、完成状态正确。
- [ ] 报工超量、重复 traceId、跨线设备和并发请求被拒绝或幂等返回。
- [ ] 一条产线故障时其他三条产线不受影响。

### E03：设备事件闭环

- [ ] MQTT/HTTP 事件通过统一 schema 校验。
- [ ] duplicate、乱序、延迟和非法 payload 有明确处理。
- [ ] telemetry 更新设备状态和指标。
- [ ] alarm.created 生成唯一活动告警。
- [ ] alarm.cleared 使用同一 alarmId 清除告警。
- [ ] Gateway/ThingsBoard 断线、重连和最后可信状态可观察。

### E04：看板与数字孪生

- [ ] 切换四条产线时设备、告警、OEE 和三维对象一致。
- [ ] 故障设备高亮、产线风险变化、恢复后状态还原。
- [ ] 设备点击、拖拽、缩放和详情联动正常。
- [ ] 页面使用统一 `deviceId`、`lineId`、`timestamp`、`dataSource`。
- [ ] 实时接口不可用时显示降级状态和最后更新时间。

### E05：ERPNext/ThingsBoard 切换与回退

- [ ] ERPNext 旁路环境、版本和许可证清单已锁定。
- [ ] ERPNext 业务对象与现有 API 完成四线对账。

## 8. 维修与设备维护实施与验收

### 8.1 当前状态

### 8.2 目标闭环


维修动作不得直接清除设备事件；只有验证通过后才能关闭维修工单，并由采集服务重新确认设备状态。设备主管负责执行，生产主管负责停机影响确认，厂长只审批高影响动作。

### 8.3 退出标准

- 计划保养逾期可查询；备件消耗先记录，库存正式扣减由 ERPNext 主责。
- 可按设备计算 MTBF、MTTR、停机时长和重复故障次数。
- 故障→维修→验证→告警清除→看板恢复有自动化和人工证据。

## 14. 升级与回滚实施与验收

### 14.1 升级策略

1. 发布前锁定代码、镜像、依赖、数据库迁移、配置和许可证清单。
2. 先备份数据库、文件和关键配置，再执行向后兼容的 expand migration。
3. 先升级影子/旁路环境，完成健康检查、接口回归和四线对账。
4. 按产线灰度，观察事件延迟、告警重复、报工幂等、库存差异和错误率。
5. 验证通过后再切换读写主责；否则保持 legacy 或 shadow 模式。

### 14.2 回滚条件与方法

触发条件包括数据对账不一致、重复扣减/报工、越权、告警丢失、设备事件无法恢复、核心 API 错误率超阈值或数据库迁移失败。回滚必须停止新写入、保留审计和失败事件，恢复上一个应用/配置版本，按备份或补偿脚本恢复数据，并重新验证四线隔离。

`MES_CORE=legacy|shadow|erpnext` 仅是受控切换开关，不是绕过审批的应急按钮；每次切换必须有操作者、原因、审批、前后版本和验证结果。

### 14.3 退出标准

- 至少完成一次影子升级、一次产线灰度和一次失败回滚演练。
- 回滚后能查询升级前数据，未确认事件不会静默丢失或重复执行。
- 数据库迁移可前滚，必要时有经验证的补偿迁移；禁止依赖手工删表。
- 发布说明、变更窗口、责任人、监控指标和恢复时限均有记录。
