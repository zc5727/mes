# 阶段 8：真实运行闭环实施计划

- 项目：MES 四产线 MPV
- 目标：完成“设备模拟器 → MQTT → 后端采集 → PostgreSQL → REST/实时看板 → 故障演练 → 最终冻结”的可重复验收
- 当前原则：不接 SaaS，不接真实 PLC，不允许策略自动控制设备；策略只生成候选方案，所有执行必须审批。
- 文档版本：阶段 8 / 2026-08-29

## 1. 本轮目标

### 必须达成

1. Mosquitto 可启动，模拟器可以发布 telemetry、`alarm.created`、`alarm.cleared`。
2. NestJS 后端能够连接、重连并重新订阅 MQTT，校验消息并更新设备/告警状态。
3. 关键实时数据从内存边界落到 PostgreSQL，重启后可恢复查询。
4. REST API、前端调用、MQTT topic、策略输入和 Nanobot 只读契约保持一致。
5. 完成单故障、多故障、Broker 断开、后端重启、重复消息和恢复演练。
6. 形成可复制的启动、停止、验收和回滚步骤，最后冻结版本。

### 明确不在本轮

- 真实设备写入、自动停线、自动执行策略。
- 多租户 SaaS、计费、云端交付。
- 复杂视觉识别、图纸 OCR、完整 AI 决策。
- 将 MQTT 原始消息直接暴露给前端。

## 3. 依赖顺序与退出条件

必须按以下顺序执行，禁止跳过前置条件：

```text
0. 清点并冻结接口契约
        ↓
1. 启动 PostgreSQL / Mosquitto / MinIO
        ↓
2. 初始化并校验 PostgreSQL schema
        ↓
3. 接入 MQTT 并验证 simulator → broker → NestJS
        ↓
4. 将 telemetry / alarm 生命周期写入 PostgreSQL
        ↓
5. REST 查询改为“数据库历史 + 内存实时态”一致读模型
        ↓
6. 前端刷新与实时推送验收
        ↓
7. 故障演练与恢复验证
        ↓
8. 全量测试、证据归档、最终冻结
```

### 0. 契约清点

退出条件：

- 前端 API 路径与后端 controller 一一对应。
- MQTT topic 只保留正式路径：
  - `mes/simulator/{tenantId}/lines/{lineId}/devices/{deviceId}/telemetry`
  - `mes/simulator/{tenantId}/alarms`
  - `mes/control/{tenantId}/simulator/command`
- Nanobot 只允许 `backend/src/agent-api/tool-contract.ts` 中的只读工具。
- 所有跨模块 ID 明确区分：`tenantId`、`lineId`、`deviceId`、`alarm.id`、`workOrderId`。

优先使用：

### 2. PostgreSQL 初始化

退出条件：

- 设备、遥测、告警、告警事件至少具备租户和来源标识。
- 唯一约束覆盖：`tenantId + deviceId + telemetry timestamp`、`tenantId + alarm.id + event`。
- 数据库不可用时，后端明确进入降级模式并记录告警，不得静默假装已落库。

### 3. MQTT 真实联调

启动后端：

```bash

```

启动四产线模拟器：

```bash

npm run dev -- --mqtt mqtt://localhost:1883 --tenant tenant-demo --seed 20260829
```

退出条件：

- 后端日志出现两条正式订阅主题。
- telemetry 到达后设备缓存和数据库均可查询。
- Broker 重启后后端自动重连并重新订阅。
- 无效 JSON、错误 topic 身份、过期 timestamp 被拒绝并产生可定位日志。

### 4. 持久化与读模型

推荐最小顺序：

1. `telemetry_events`：保存原始合法遥测事件。
2. `device_current_state`：保存设备最新状态，按租户/设备唯一。
3. `alarm_events`：保存 created/cleared 事件，按租户/告警/事件幂等。
4. `alarm_current_state`：保存当前 active/cleared 状态。
5. REST 查询统一读取 current state，历史接口读取 events。

退出条件：

- 后端重启后设备状态和活跃告警不丢失。
- 重复 MQTT 消息不会产生重复记录。
- 数据库写入失败时消息不会被错误标记为已处理。
- 内存缓存只作为实时加速层，不作为唯一事实来源。

### 5. 前端与实时看板

当前前端核心调用：

- `GET /production-lines`
- `GET /devices`
- `GET /work-orders/overview`
- `GET /agvs`
- `GET /alarms`

退出条件：

- `VITE_API_BASE_URL` 和 `VITE_TENANT_ID` 与后端一致。
- 故障后设备、产线、告警、看板统计最终一致。
- 前端降级状态有明确提示，不能把 mock/旧台账显示为实时数据。
- WebSocket 若未完成后端推送，则本轮只验收 REST 刷新，不宣称实时闭环完成。

## 5. 阻塞清单

### P0：不解决不能宣称“真实运行闭环完成”

1. PostgreSQL 尚未接入 MQTT 采集主链路，后端重启会丢失实时态和告警态。
2. 缺少可重复执行的数据库 migration/schema 初始化。
3. 端到端 Broker 重启和后端重启演练尚未形成自动化证据。

### P1：不解决只能称为“可演示闭环”

1. 前端 WebSocket 客户端已有，但后端 MQTT→WebSocket 推送未完整装配。
2. 告警历史、清除时间和生命周期审计接口不足。
3. 策略仿真结果没有统一 REST 查询和持久化。
4. Nanobot 只有契约，缺少 adapter、身份校验、权限和 trace 审计。
5. 前端部分可选接口失败时静默降级，生产环境需要可观测提示。

### P2：生产化前必须解决

1. Mosquitto 匿名访问需替换为账号、ACL、TLS。
2. 数据库备份、恢复、连接池、迁移回滚和监控尚未配置。
3. 启动脚本默认不打开 MQTT 是开发模式的显式选择；传入 `--infra --mqtt` 时会
   执行 PostgreSQL/MQTT readiness 和 Backend health 检查。当前 macOS/Codex
   非交互执行器可能在命令返回后清理子进程，进程脱离能力尚未形成可靠验收证据。
4. 真实设备协议适配、写入权限和安全联锁尚未设计。

## 6. 启动脚本和冻结要求

### 启动脚本要求

最终脚本至少提供：

```bash
./scripts/dev-up.sh       # 基础设施、后端、前端、模拟器按依赖顺序启动
./scripts/dev-down.sh     # 反向停止并清理 PID
./scripts/verify-all.sh   # env、build、unit、e2e、MQTT smoke、前端 build
```

脚本必须：

- 检查端口占用和依赖 readiness。
- 不把真实密码写入脚本。
- 记录 PID、版本、环境变量开关和日志路径。
- 后端未健康时不得宣布“启动成功”。
- `dev-down` 必须能清理异常退出后残留进程。

### 最终冻结门禁

冻结前必须同时满足：

- `git diff --check` 通过。
- 后端 env、unit、e2e、build 全部通过。
- 模拟器 build/test 全部通过。
- 前端 build 通过。
- A03-A10、A12、A14-A16 有命令和日志/API 响应证据。
- 仓库不包含 `.env`、密钥、生产 MQTT 凭据和临时日志。
- 生成冻结清单、已知问题清单、回滚版本和下一阶段任务。
- 未完成项不得通过“前端可显示”替代验收，必须标记为部分实现或阻塞。

## 7. 最终交付判断

阶段 8 的交付结论只允许使用以下三种状态：

- **通过**：MQTT、PostgreSQL、后端、前端和故障恢复均有可重复证据。
- **部分通过**：模拟器、MQTT、后端内存态和 REST 展示可用，但数据库恢复或实时推送未完成。
- **阻塞**：核心消息无法稳定采集、租户/设备身份不一致、重连后不恢复，或存在自动控制越权风险。

在 PostgreSQL 持久化、重启恢复和真实故障演练完成前，本项目只能标记为“部分通过”，不能标记为生产可用。
