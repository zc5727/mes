# MES 开发验证清单

> 适用范围：当前 MVP / MPV 联调版本。本文档以现有代码为准，不把规划中的能力误记为已交付能力。
>
> 当前主链路：`模拟器 → MQTT → NestJS 内存采集 → REST 查询 → 数字孪生前端`。

## 1. 当前实现状态

### 已实现

- NestJS 模块化单体后端，统一前缀 `/api/v1`。
- 基础 REST：健康检查、租户、工厂、产线、设备、订单、工单、AGV、告警、看板。
- MQTT ingestion：
  - 连接 Mosquitto。
  - 订阅 telemetry 和 alarms 通配主题。
  - 校验 JSON、租户、产线、设备及枚举字段。
  - 内存缓存最新设备遥测，拒绝重复和过期数据。
  - 告警 created/cleared 幂等去重。
  - 处理 connect、reconnect、close、offline 和订阅失败边界。
- 模拟器支持 MQTT 发布、故障注入、快照和基础控制命令。
- 前端已通过 REST 拉取产线、设备、工单、AGV、告警和看板概览。
- 策略引擎已具备纯内存、只读输入的候选方案模拟：故障转移、负载均衡、物料短缺、恢复和延期风险。
- Nanobot 只读工具契约已定义，禁止直接控制设备、产线或发布 MQTT。

### 部分实现

- 数字孪生当前以 REST 首次加载为主；WebSocket 客户端协议已存在，但后端实时 WebSocket 服务尚未形成完整闭环。
- MQTT 采集数据目前进入进程内缓存，尚未持久化到 PostgreSQL，也没有消息重放和历史查询。
- `/api/v1/alarms` 能合并基础设备告警与 MQTT 活跃告警，但 cleared 告警不会形成历史记录接口。
- 策略引擎是服务层能力，当前没有完整的策略仿真 REST 编排、结果持久化和审批执行链路。
- Nanobot 契约已定义，但后端尚未提供完整的工具路由适配器；本地 nanobot 接入尚未验收。

### 未实现或明确延期

- SaaS 多租户隔离、计费、云端交付。
- 真实 PLC/OPC UA/Modbus 适配和写入控制。
- 自动停线、自动执行策略和无审批控制。
- PostgreSQL/时序数据库持久化、对象存储、消息重放。
- 复杂视觉图纸分析、OCR 和生产质量 AI 闭环。
- 完整认证、细粒度权限、审计闭环和生产级高可用部署。

| GET/POST/PATCH/DELETE | `/factories`、`/factories/:id` | 已实现 | 工厂基础资料 |
| GET | `/production-lines`、`/production-lines/:id` | 已实现 | 产线查询 |
| GET | `/production-lines/overview` | 已实现 | 产线概览 |
| POST/PATCH/DELETE | `/production-lines`、`/production-lines/:id...` | 已实现 | 产线维护和状态变更 |
| GET | `/devices`、`/devices/:id` | 已实现 | 设备台账查询 |
| GET | `/devices/overview` | 已实现 | 设备概览 |
| POST/PATCH/DELETE | `/devices`、`/devices/:id...` | 已实现 | 设备维护、状态和手工 telemetry |
| GET/POST | `/orders`、`/orders/:id` | 已实现 | 订单查询和创建 |
| GET/POST/PATCH/DELETE | `/work-orders`、`/work-orders/:id...` | 已实现 | 工单、状态、报工和报工记录 |

| PATCH | `/alarms/:id/acknowledge` | 已实现 | 告警确认 |
| PATCH | `/alarms/:id/close` | 已实现 | 告警关闭 |

| POST | `/simulator/control` | 已实现 | 发布模拟器控制命令；仅发布 MQTT，不执行真实设备控制 |
| GET/POST/PATCH | `/foundation/...` | 已实现 | 质量记录、文档、策略、审计基础接口 |

### API 与前端当前调用关系

前端文件：`third_party/threejs-factory-demo/src/api/mesApi.ts`。

首次加载 `fetchFactorySnapshot()` 会调用：

- 必选：`GET /production-lines`
- 必选：`GET /devices`
- 必选：`GET /work-orders/overview`
- 可选降级：`GET /agvs`
- 可选降级：`GET /alarms`
- 可选降级：`GET /dashboard/overview`

前端默认配置：

- `VITE_API_BASE_URL=http://localhost:3000/api/v1`
- `VITE_TENANT_ID=tenant-demo`
- 请求头：`x-tenant-id: tenant-demo`

风险：前端对 AGV、告警和看板接口采用可选降级，接口失败时仍可能显示基础台账数据，验收时必须区分“真实 API 数据”和“降级数据”。

## 3. MQTT 接口契约

### 3.1 Broker 与环境变量

```dotenv
MQTT_ENABLED=false
MQTT_URL=mqtt://localhost:1883
```

只有在 `MQTT_ENABLED=true` 且 `MQTT_URL` 有效时，后端才创建 MQTT 客户端；默认 HTTP-only 启动不会连接 Broker。

现有 Mosquitto 配置：`backend/infra/mosquitto.conf`，开发环境允许匿名连接，不代表生产配置。

### 3.2 后端订阅主题

```text
mes/simulator/+/lines/+/devices/+/telemetry
mes/simulator/+/alarms
```

telemetry 消息：

```json
{
  "event": "device.telemetry",
  "data": {
    "deviceId": "cnc-01",
    "deviceName": "CNC-01",
    "lineId": "line-cnc",
    "status": "RUNNING",
    "temperatureCelsius": 42,
    "cycleTimeSeconds": 42,
    "totalCount": 3,
    "goodCount": 3,
    "defectCount": 0,
    "activeFaults": [],
    "timestamp": "2026-08-28T09:00:00.000Z"
  }
}
```

告警消息：

```json
{
  "event": "alarm.created",
  "data": {
    "id": "line-cnc-cnc-01-OVERHEAT",
    "lineId": "line-cnc",
    "deviceId": "cnc-01",
    "type": "OVERHEAT",
    "severity": "CRITICAL",
    "message": "设备温度超过安全阈值",
    "startedAt": "2026-08-28T09:00:00.000Z"
  }
}
```

清除告警使用同一主题，将事件改为 `alarm.cleared`，并提供合法的 `clearedAt`。

### 3.3 MQTT 控制主题

后端 `/simulator/control` 发布：

```text
mes/control/{tenantId}/simulator/command
```

模拟器当前同时兼容：

```text
mes/control/{tenantId}/twin/command
mes/control/{tenantId}/simulator/command
mes/control/{tenantId}/simulator
```

因此当前控制主题已经统一兼容，但生产接入仍应只保留 `simulator/command` 作为正式契约，避免继续扩散别名。

## 4. 策略引擎对照

实现位置：`backend/src/strategies/strategy-engine.service.ts`。

| 能力 | 状态 | 说明 |
|---|---|---|
| 设备故障风险识别 | 已实现 | 识别 alarm/offline 设备 |
| 产线负载风险识别 | 已实现 | 按未来 8 小时产能估算 |
| 物料短缺风险 | 已实现 | 输出受影响工单 |
| 工单延期风险 | 已实现 | 基于剩余数量、交期和固定估算 |
| 任务转移候选方案 | 已实现 | 仅生成建议 |
| 负载均衡候选方案 | 已实现 | 仅生成建议 |
| 维修恢复候选方案 | 已实现 | 仅生成建议 |
| 方案评分和推荐 | 已实现 | 结果含 `requiresApproval: true` |
| 仿真结果 API/历史 | 未实现 | 目前没有完整外部编排和持久化 |
| 审批、执行、回滚 | 未实现 | 禁止自动执行 |

策略引擎当前是确定性纯函数式服务边界，输入为 `StrategySnapshot`，输出为 `StrategySimulationResult`。不能把候选方案当作已执行动作。

## 5. Nanobot 对照

契约文件：`backend/src/agent-api/tool-contract.ts`；说明文件：`docs/nanobot只读工具契约.md`。

已定义只读工具：

- `get_production_overview`
- `get_line_status`
- `get_device_status`
- `get_active_alarms`
- `get_work_order_progress`
- `get_delay_risk`
- `get_simulation_snapshot`
- `get_strategy_result`

每次调用应包含 `tool`、`arguments`、`tenantId`、`traceId`，响应包含 `ok`、`tool`、`traceId` 和 `data` 或结构化 `error`。

当前差异：

- 契约已定义，但完整的后端工具路由、参数校验、权限校验和 trace 审计尚未完成。
- Nanobot 暂时只能查询和分析，不能直接调用 `/simulator/control`，不能发布 MQTT。
- `get_simulation_snapshot`、`get_strategy_result` 尚无完整统一的数据源和持久化结果接口。

故障验收：

1. 对模拟器注入 `OVERHEAT` 或 `JAM`。
2. 确认后端日志已订阅 MQTT，且 `/dashboard/overview` 的设备统计和温度趋势发生变化。
3. 确认 `/alarms` 出现 `mqtt-alarm-{tenantId}-{alarmId}`。
4. 停止故障持续上报后，发布同一 `alarm.id` 的 `alarm.cleared`。
5. 确认该告警从 active 列表消失，再重复发布 cleared，结果不重复、不报错。
6. 发布相同 telemetry 两次和一条旧 timestamp telemetry，确认缓存只保留最新数据。

## 7. 阻塞项与质量门禁

### 当前阻塞项

1. MQTT 数据只在内存中，后端重启会丢失实时缓存和告警状态。
2. 告警 cleared 目前只影响活跃查询，缺少告警历史和生命周期审计接口。
3. Nanobot 只有只读契约，尚无完整 API adapter、认证、权限和 trace 审计。
4. 策略只有候选方案生成，尚无仿真场景持久化、结果查询和审批工作流。
5. 前端实时 WebSocket 与后端 MQTT 尚未打通为统一推送链路。
6. Mosquitto 当前开发配置为匿名访问，不能直接用于生产。

### 每次提交前

- `git diff --check`
- 后端 `verify:env`
- 后端 mock、unit、e2e、build
- 前端 build
- 至少执行一次 telemetry、alarm.created、alarm.cleared 联调
- 确认没有提交 `backend/.env`、真实凭据或生产 MQTT 配置

## 8. 本轮接口一致性结论

- REST 基础路径、租户请求头和前端默认 API 地址一致。
- 前端使用的核心查询接口均已存在；部分接口失败时会静默降级，需要在生产前增加可观测提示。
- 模拟器 telemetry/alarms 主题与后端订阅主题一致。
- 模拟器控制主题目前兼容后端发布路径，但应将 `simulator/command` 固化为唯一正式主题。
- 策略服务、Nanobot 契约和 REST 路由之间仍存在“定义完成但未完全装配”的差异，这是下一阶段主要集成工作。
