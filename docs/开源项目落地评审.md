# 开源项目落地评审：ERPNext、ThingsBoard、BaSyx（OpenMES 历史候选）

## 1. 评审结论

四个项目不应被当作四套 MES 代码拼接。它们分别处在不同层次：

```text
ERPNext       = ERP/供应链/制造基础业务
ERPNext       = 当前生产业务底座候选
OpenMES       = 历史候选与功能域参考
ThingsBoard   = IoT 设备接入、遥测、规则和可视化平台
BaSyx         = 工业资产语义、AAS 数字资产模型和工业互操作基础设施
```

对当前项目的建议：

1. **不直接把 ERPNext 或 OpenMES 源码嵌入当前 NestJS 主服务。** 通过独立部署和 Integration adapter 隔离许可证与技术栈耦合。
2. **ThingsBoard 可作为可选设备连接/遥测平台**，优先评估 ThingsBoard Gateway/Edge 和 MQTT、HTTP、CoAP 接入能力；MES 仍拥有生产、工单、质量和追溯主数据。
3. **BaSyx 适合作为设备/资产语义层和数字孪生元数据层**，不替代 MES 生产执行系统。
4. 当前项目继续以自有 NestJS MES 核心为主，采用 API、MQTT、事件和插件/Sidecar 与外部开源系统解耦。
5. 第一阶段只复用 Apache-2.0、MIT、BSD 等许可证明确且边界清晰的组件；GPL/AGPL 项目先做外部服务集成和业务参考，不复制核心代码。

## 2. 项目对比

| 项目 | 定位 | 适合复用 | 不适合承担 | 当前建议 |
|---|---|---|---|---|
| ERPNext | ERP + 制造管理 | 物料、采购、库存、BOM、财务、基础制造流程 | 实时设备状态、数字孪生、毫秒级采集 | 作为 ERP 候选，通过 API/消息集成 |
| ERPNext | 生产业务底座 | 订单、制造、工单、物料、质量、资产和生产流程 | 当前 NestJS 核心的直接依赖 | 独立部署，通过 adapter 接入 |
| OpenMES | 历史候选/现场 MES 参考 | 工单、批次、质量、停机、Andon、追溯、审计、排程业务参考 | 当前架构生产底座 | 不再作为当前切换目标 |
| ThingsBoard | IoT 平台 | 设备注册、遥测、规则链、告警、仪表盘、边缘接入 | 工艺路线、WIP、工单、批次 genealogy | 可选设备遥测基础设施 |
| BaSyx | AAS/工业互操作 | 资产模型、子模型、设备语义、AASX、注册和发现 | 订单、工单、质量判定、库存 | 作为资产语义和数字孪生元数据层 |

## 3. 许可证和落地风险

### ERPNext

ERPNext GitHub 仓库标注为 GPL-3.0。若直接修改、组合或分发其代码，需要由法务确认 GPL 义务、衍生作品范围和网络交付场景。ERPNext 功能覆盖 ERP、库存、采购、制造、资产和项目等业务。[ERPNext GitHub](https://github.com/frappe/erpnext)

**建议：**不复制 ERPNext 源码到当前 TypeScript/NestJS 项目；将 ERPNext 作为独立系统，通过 REST、Webhook、文件交换或消息总线进行订单、物料、库存和报工集成。

### OpenMES

OpenMES 当前仓库标注为 AGPL-3.0，并提供 MQTT、REST、CSV/XLS、工单、批次、质量、停机、追溯和审计等能力。[OpenMES GitHub](https://github.com/Mes-Open/OpenMes)

AGPL 对网络提供服务的源代码提供义务尤其需要重视。不能因为“只调用接口”就默认没有许可证风险，具体是否形成衍生作品或组合分发应交由法务确认。

**建议：**只借鉴模块和数据流程；若需要运行 OpenMES，作为独立外部应用，不把其代码拷贝到本项目。

### ThingsBoard

ThingsBoard 主仓库标注 Apache-2.0，定位是设备管理、数据采集、处理和可视化平台。[ThingsBoard GitHub](https://github.com/thingsboard/thingsboard)

Apache-2.0 对商业集成更友好，但仍需要保留版权和许可证声明，并核查依赖树、Enterprise/Community 边界以及各插件的单独许可证。

**建议：**可以作为候选外部 IoT/边缘层；正式采用前固定版本、导出 SBOM，并进行性能和数据主权评估。

### BaSyx

BaSyx Python SDK 和 Java Server SDK 标注 MIT，支持 AAS v3、JSON/XML/AASX、Repository、Registry、Submodel 和相关服务。[BaSyx Python SDK](https://github.com/eclipse-basyx/basyx-python-sdk) [BaSyx Java Server SDK](https://github.com/eclipse-basyx/basyx-java-server-sdk)

MIT 对嵌入式复用较友好，但仍需检查 NOTICE、第三方依赖和具体组件版本。

**建议：**优先评估 BaSyx 的资产模型和服务，不引入完整 Java 运行时到 NestJS 主进程；通过独立 BaSyx 服务或 TypeScript/Python SDK 连接。

## 4. 成熟度和适用性判断

### ERPNext：业务成熟度高，MES 实时性不是重点

适合承担：

```text
物料主数据
BOM
采购
库存
供应商
销售订单
制造订单
财务和成本
```

不适合直接承担：

```text
设备秒级遥测
PLC/机器人连接
数字孪生实时状态
设备级告警闭环
产线实时控制
```

### OpenMES：现场 MES 业务参考价值高

适合借鉴：

```text
工单生命周期
批次生产
工艺模板
质量检查
停机原因
问题/Andon
现场平板操作
审计追溯
生产排程
```

但应重点验证：

- 代码和文档是否满足当前项目二次开发需要；
- MQTT 采集是否达到真实工厂规模；
- 数据库模型是否适合当前四条产线和未来多工厂；
- AGPL 对产品交付模式的影响。

### ThingsBoard：设备接入成熟，业务语义需要 MES 补齐

适合承担：

```text
设备注册
设备凭据
MQTT/HTTP/CoAP 接入
遥测存储
属性管理
规则链
设备告警
边缘节点
基础仪表盘
```

不应让它成为：

```text
MES 工单中心
生产执行中心
工艺路线中心
批次追溯中心
质量放行中心
```

### BaSyx：语义和资产模型价值高，不是 MES 业务系统

适合承担：

```text
设备身份
资产层级
设备技术属性
AAS Submodel
设备能力描述
数字产品护照相关元数据
资产发现和互操作
```

不承担：

```text
订单排程
工单执行
物料库存
质量判定
生产报工
维修业务闭环
```

## 5. 推荐目标组合

### 方案 A：当前阶段推荐

```text
NestJS MES 核心
  + 自有统一设备事件中心
  + 独立驱动中心
  + PostgreSQL
  + 当前四条产线模拟器
  + 可选 BaSyx 资产语义服务
```

适用于当前核心闭环和仿真阶段，系统边界最清晰。

### 方案 B：设备数量增长后

```text
ThingsBoard Edge/Gateway
  → MQTT/HTTP
  → MES 统一事件中心
  → 生产/质量/维护/追溯
```

适用于设备数量增加、协议种类增加、需要边缘离线运行的场景。

### 方案 C：ERP 集成阶段

```text
ERPNext
  ⇄ Integration Adapter
  ⇄ NestJS MES
```

ERPNext 管理企业级订单、采购、物料和库存；MES 管理现场执行、设备、质量、WIP 和生产实时状态。

### 不推荐方案

```text
ERPNext + OpenMES + ThingsBoard + BaSyx
全部源码合并到一个应用
```

原因：技术栈、数据库、许可证、身份体系、事件模型和主数据边界都会迅速复杂化。

## 7. 落地实施顺序

### 第 1 阶段：不引入外部整套系统

1. 冻结统一设备事件 Schema；
2. 把当前模拟器改为统一事件生产者；
3. 把 MQTT parser 改为通用 Payload 映射；
4. 增加 HTTP Webhook；
5. 增加连接管理和点位管理；
6. 增加事件落库和 current-state。

### 第 2 阶段：引入成熟协议组件

1. 复用开源 MQTT 客户端；
2. 复用开源 Modbus Client；
3. 复用开源 OPC UA Client；
4. 驱动放在独立边缘运行时；
5. 使用模拟服务器和故障注入进行回归测试。

### 第 3 阶段：评估 ThingsBoard

仅在以下条件满足后评估：

- 设备连接数量明显增加；
- 需要边缘离线能力；
- 当前自有驱动中心维护成本过高；
- 已明确 ThingsBoard 与 MES 的设备主数据归属；
- 已完成 Apache-2.0 和依赖许可证审查。

### 第 4 阶段：引入 BaSyx

优先用于：

- 设备资产档案；
- 设备能力模型；
- 数字孪生元数据；
- 跨系统设备语义统一；
- AASX 导入导出。

### 第 5 阶段：ERPNext 集成

优先只做：

```text
ERPNext → MES：订单、物料、BOM、交期
MES → ERPNext：生产进度、报工、完工、质量结果
```

不直接共享数据库，不让 ERPNext 绕过 MES 修改设备状态和现场执行状态。

## 8. 评审门禁

任何开源代码进入仓库前必须提交：

```text
项目名称和版本
Git commit/tag
许可证
NOTICE/LICENSE 文件
依赖树和 SBOM
修改清单
安全扫描结果
性能测试结果
数据和身份边界
退出替代方案
```

任何外部平台接入前必须明确：

- 谁拥有设备主数据；
- 谁拥有实时状态；
- 谁拥有告警；
- 谁拥有生产事件；
- 谁拥有历史数据；
- 哪一侧负责租户隔离；
- 哪一侧负责权限和审计。

## 9. 最终决策

当前不做源码大合并，采用以下路线：

```text
当前：自有 NestJS MES 核心 + 独立驱动中心
协议：优先复用成熟开源协议库
设备平台：按需要评估 ThingsBoard
资产语义：逐步引入 BaSyx
ERP：后续通过适配器接入 ERPNext
OpenMES：只作为业务流程和模块设计参考
```

这条路线能保留当前四条产线仿真和 MES 核心开发节奏，同时避免在早期引入 GPL/AGPL 代码、异构数据库和多个重复主数据中心。

## 10. 落到当前代码的差距

### 10.1 当前已有能力

当前仓库已经具备可继续演进的骨架：

| 当前代码 | 已有能力 | 与成熟项目的对应关系 |
|---|---|---|
| `backend/src/devices` | 设备台账、协议字段、状态和 telemetry HTTP 接口 | 对应设备主数据和基础采集入口 |
| `backend/src/mqtt` | MQTT 连接、订阅、模拟器 telemetry/alarm 解析、内存缓存和告警去重 | 对应 IoT/MES 采集入口，但仍绑定模拟器契约 |
| `backend/src/orders` | 生产订单、进度和状态 | 对应 ERP/MES 订单入口 |
| `backend/src/work-orders` | 工单状态机、报工、批次号、序列号校验 | 已有最小生产执行闭环 |
| `backend/src/strategies` | 只读策略仿真和候选建议 | 可扩展为排程/产能决策层 |
| `backend/prisma/schema.prisma` | Tenant、Factory、Line、Device、Order、WorkOrder、Alarm 等关系 | 已有基础关系模型，但事件历史和配置模型不足 |
| `simulator/src` | 四条产线、设备、AGV、告警和固定种子回归 | 可作为所有驱动和事件契约的测试源 |

### 10.2 关键差距

| 差距 | 当前证据 | 成熟项目可借鉴点 | 影响 |
|---|---|---|---|
| 采集协议不通用 | `mqtt-parser.ts` 使用 `mes/simulator/...` 固定 Topic 和固定字段 | ThingsBoard 的设备/遥测接入抽象；OpenMES 的机器连接入口 | 真实厂商 MQTT/网关报文会被拒绝 |
| OPC UA/Modbus 未落地 | DTO 支持 `opcua`、`modbus-tcp`，但没有 driver/runtime | ThingsBoard Gateway、MES AI Sidecar、开源协议 SDK | 目前不能直接连接 PLC、仪表、CNC |
| 设备连接配置不足 | `Device` 只有 `protocol`、`metadata` | 连接、凭据、点位、采集任务独立建模 | 无法规模化管理设备 |
| 无统一点位/语义模型 | `metrics` 为自由 JSON | BaSyx AAS/Submodel；OPC UA NodeId/质量码 | 同一指标在不同设备间无法稳定复用 |
| 实时态主要在内存 | `DeviceTelemetryCache`、`AlarmDeduplicator` | ThingsBoard 时序/当前值分层；MES AI 持久化和事件总线 | 重启丢状态、无法追溯历史 |
| 业务模型仍是最小闭环 | 工单和报工已有，但没有工艺路线、工序、WIP、物料消耗 | OpenMES、Odoo MRP、ERPNext Manufacturing | 不能完整表达现场工序执行 |
| 质量模型缺失 | 视觉/质量数据没有独立事件和检验模型 | OpenMES 质量检查；Odoo quality；ERPNext Quality | 无法形成质量放行和追溯闭环 |
| 维护模型缺失 | 只有设备状态、告警和策略风险 | OpenMES maintenance/停机；Odoo maintenance | 告警不能转维修工单 |
| 外部集成边界未冻结 | 订单有 `externalId`/`externalSystem`，但没有 integration job、outbox、同步游标 | ERPNext/Odoo 作为 ERP 外部系统 | 订单、物料、报工同步容易重复或丢失 |
| 资产语义缺失 | 数字孪生有设备身份，但没有标准资产子模型 | BaSyx AAS 和子模型 | 跨系统设备能力、属性和资产档案不统一 |

## 12. 可直接执行的补齐优先级

### P0：先修采集基础，不引入整套外部 MES

1. 新增 `DeviceConnection`、`DevicePoint`、`DeviceEvent` 设计；
2. 将 `mqtt-parser.ts` 拆为通用 MQTT Driver 和 simulator adapter；
3. 保留当前模拟器协议作为一个兼容 adapter，而不是继续作为唯一协议；
4. 建立 JSON Schema 和统一事件校验；
5. 增加 HTTP Webhook 的签名、幂等和批量上报；
6. 原始合法事件落库，更新设备 current-state；
7. 为断线、重复、乱序、过期和错误质量码增加测试。

### P1：复用协议开源代码，形成独立驱动中心

1. 选定并锁定 MQTT、Modbus TCP、OPC UA 开源依赖版本；
2. 驱动以独立 Node/Python/Java Sidecar 运行，不放进 NestJS 业务进程；
3. 统一提供 `connect`、`disconnect`、`healthCheck`、`read`、`subscribe`；
4. 用 Modbus/OPC UA 模拟服务器接入当前四条产线；
5. 增加连接测试、驱动健康、采集延迟和解析错误 API；
6. 仅支持只读采集，暂不实现真实设备写入。

### P2：补齐 MES 生产执行

1. 产品、BOM、工艺路线、工序和工作中心；
2. 工单和工序任务拆分；
3. 开工、暂停、完工、转序、返工和取消；
4. 物料领用、消耗、退料；
5. WIP、批次、序列号和 genealogy；
6. 设备 telemetry/production event 自动生成报工草稿，但必须保留人工确认策略。

### P3：补质量和维护闭环

1. 检验计划、质量特性、不良代码和检验结果；
2. 接入视觉检测结果、图片和 traceId；
3. 告警转维护工单；
4. 点检、保养、维修、备件和恢复验证；
5. 统计 MTBF、MTTR、停机原因和设备健康评分。

### P4：按需引入外部平台

1. 设备规模和离线需求达到阈值后，评估 ThingsBoard Edge/Gateway；
2. 资产模型稳定后，引入 BaSyx AAS/Submodel；
3. ERP 需求明确后，通过 adapter 接入 ERPNext 或 Odoo；
4. 不共享外部系统数据库，不让外部系统绕过 MES 修改现场状态。

## 13. 产品经理验收口径

本计划进入开发前，产品经理必须确认：

- P0 是否明确到 API、数据表和验收场景；
