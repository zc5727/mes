# MES 阶段 8：PostgreSQL / Prisma 数据持久化设计与迁移计划

> 版本：v0.1  
> 状态：设计基线，不启用数据库写入  
> 适用范围：订单、工单、设备、告警、策略仿真  
> 原则：不破坏当前内存 MVP，先完成可评审的数据边界，再分阶段切换持久化。

## 1. 目标与非目标

### 1.1 目标

- 将当前内存实体映射为稳定的 PostgreSQL 关系模型。
- 保留现有 API 字段和状态值，避免数据库迁移反向耦合前端和策略引擎。
- 保证工单报工可追溯到设备和采集来源。
- 为四条产线、多设备、多租户预留关系和索引。
- 使工单数量、状态流转、告警去重可以由应用层和数据库层双重约束。
- 支持先读后写、按模块灰度切换和回滚。

### 1.2 暂不实施

- 不新增 Prisma 依赖或修改 AppModule。
- 不启用生产数据库连接。
- 不迁移 MQTT 原始消息和设备缓存表。
- 不设计 ERP、采购、财务、仓储和高级 APS 表。
- 不把策略模拟建议直接落库为设备控制指令。

## 2. 当前 MVP 到持久化模型的映射

| 当前模块 | 目标表 | 优先级 | 说明 |
|---|---|---:|---|
| factories / production-lines | factories / production_lines | P1 | 工单绑定产线的外键来源 |
| devices | devices | P1 | 设备主数据；实时遥测另行处理 |
| orders | production_orders | P1 | 生产订单主表 |
| work-orders | work_orders | P1 | 生产工单主表 |
| work-orders.report | work_order_reports | P1 | 追加报工，不覆盖历史 |
| alarms | alarms | P2 | 告警事件和处理状态 |
| strategies | strategy_runs / strategy_candidates | P2 | 仿真结果，不代表执行指令 |
| MQTT telemetry | telemetry_events | P3 | 需要历史追溯时再建设 |

## 3. 关系模型

    tenants
      ├── factories
      │     └── production_lines
      │           └── devices
      │                 ├── work_order_reports
      │                 └── alarms
      ├── production_orders
      │     └── work_orders
      │           └── work_order_reports
      └── strategy_runs
            └── strategy_candidates

    work_orders ──< work_order_status_history
    work_orders ──< work_order_reports
    devices ──────< work_order_reports

关键关系：

1. 一个租户可以有多个工厂，一个工厂可以有多条产线。
2. 一个产线可以有多台设备。
3. 一个生产订单可以拆分为多个工单。
4. 一个工单只能绑定一个有效产线。
5. 一个工单可以有多条报工记录。
6. 报工记录可选绑定设备；绑定后必须属于同一租户和工单产线。
7. 工单状态变化追加状态历史，不通过覆盖主表丢失轨迹。
8. 策略仿真只引用快照和业务实体 ID，不直接修改设备或工单。

## 4. 推荐 Prisma Schema 草案

以下为迁移设计草案，暂不写入 backend/prisma/schema.prisma，避免当前 MVP 引入数据库依赖。

核心模型及字段：

### Tenant

- id：字符串主键
- name：租户名称
- created_at、updated_at

### Factory

- id、tenant_id、code、name
- tenant_id + code 唯一
- tenant_id 索引

### ProductionLine

- id、tenant_id、factory_id、code、name
- active、target_oee
- tenant_id + code 唯一
- tenant_id + factory_id 索引

### Device

- id、tenant_id、line_id、code、name
- model、protocol、status、status_reason
- last_seen_at、metadata、created_at、updated_at
- tenant_id + code 唯一
- tenant_id + line_id + status 索引

### ProductionOrder

- id、tenant_id、order_no、product_code、product_name
- planned_qty、completed_qty、due_at、priority、status
- tenant_id + order_no 唯一
- tenant_id + status + due_at 索引

### WorkOrder

- id、tenant_id、order_id、order_no
- product_code、product_name、line_id
- planned_qty、completed_qty、due_at、priority
- status、status_reason、version、created_at、updated_at
- tenant_id + order_no 唯一
- tenant_id + status + due_at 索引
- tenant_id + line_id + status 索引

### WorkOrderReport

- id、tenant_id、work_order_id、device_id
- quantity、good_qty、defect_qty
- source_trace_id、reported_at、created_at
- tenant_id + source_trace_id 唯一，保证幂等
- tenant_id + work_order_id + reported_at 索引
- tenant_id + device_id + reported_at 索引

### WorkOrderStatusHistory

- id、tenant_id、work_order_id
- from_status、to_status、reason、occurred_at、operator_id
- tenant_id + work_order_id + occurred_at 索引

### Alarm

- id、tenant_id、line_id、device_id、code
- level、status、message、dedupe_key
- occurred_at、resolved_at、created_at、updated_at
- tenant_id + status + level + occurred_at 索引

### StrategyRun / StrategyCandidate

StrategyRun 保存 simulation_id、snapshot_at、generated_at、snapshot、risks；StrategyCandidate 保存 action、risk、affected_orders、from_line、to_line、expected_finish_time、expected_impact、reason、requires_approval、score。

策略结果属于历史分析数据，不应成为设备控制命令。

## 5. 关系和删除策略

- 所有业务表保留 tenant_id，查询和写入必须带租户条件。
- tenant、factory、production_line、device、order、work-order 默认 Restrict 删除。
- 已有报工的工单禁止物理删除，使用 cancelled 或归档字段。
- strategy_candidate 随 strategy_run Cascade 删除，仅限仿真临时结果；正式审计版本应改为软删除。
- 生产数据的时间字段用 PostgreSQL timestamptz，接口继续输出 ISO 8601。

## 6. 数据库约束

Prisma 不能完整表达跨列约束，需在 SQL migration 中补充：

    ALTER TABLE production_orders
      ADD CONSTRAINT production_orders_qty_check
      CHECK (planned_qty > 0 AND completed_qty >= 0 AND completed_qty <= planned_qty);

    ALTER TABLE work_orders
      ADD CONSTRAINT work_orders_qty_check
      CHECK (planned_qty > 0 AND completed_qty >= 0 AND completed_qty <= planned_qty);

    ALTER TABLE work_order_reports
      ADD CONSTRAINT work_order_reports_qty_check
      CHECK (
        quantity > 0
        AND good_qty >= 0
        AND defect_qty >= 0
        AND good_qty + defect_qty = quantity
      );

    CREATE UNIQUE INDEX work_order_reports_trace_unique
      ON work_order_reports (tenant_id, source_trace_id);

应用层仍须校验：

- 工单绑定产线存在且属于当前租户。
- 订单存在且属于当前租户。
- 报工设备存在、属于当前租户并属于工单产线。
- 暂停和取消必须有原因。
- completed 只能在 completed_qty = planned_qty 时产生。
- 状态只能按当前状态机迁移。

## 7. 报工事务边界

持久化后，报工接口必须在一个数据库事务内完成：

1. 锁定工单行（SELECT FOR UPDATE），或使用 version 乐观锁。
2. 校验租户、状态、产线和数量。
3. 用 source_trace_id 做幂等查询，重复请求返回原报工结果。
4. 新增 work_order_reports。
5. 更新 work_orders.completed_qty。
6. 数量达到计划时更新为 completed。
7. 更新关联 production_orders.completed_qty。
8. 状态变化时写入 work_order_status_history。
9. 提交事务。

不能把以上步骤拆成多个无事务的独立写操作，否则并发报工可能超产。

## 8. 迁移分期计划

### P0：契约冻结（0.5～1 天）

- 冻结现有 DTO、状态值和响应字段。
- 继续使用字符串 ID，不改成自增整数。
- 时间统一 UTC 存储，接口使用 ISO 8601。
- 明确 source_trace_id 的幂等语义。

验收：现有 MVP 定向测试和 build 不受影响。

### P1：基础主数据和订单工单（1～2 天）

- 建立 tenants、factories、production_lines、devices。
- 建立 production_orders、work_orders。
- 增加外键、租户联合唯一索引和数量 CHECK。
- 编写四条产线、每条 3～5 台设备的种子数据。

验收：数据库只读查询与当前内存 API 返回结构一致。

### P2：报工和审计（1～2 天）

- 建立 work_order_reports、work_order_status_history。
- 实现事务报工、幂等和并发保护。
- 增加内存数据导入 dry-run 校验。
- 先让查询走数据库，写入保留开关。

验收：重复报工不产生重复记录；并发报工不超过计划数。

### P3：告警和策略结果（1～2 天）

- 建立 alarms。
- 建立 strategy_runs、strategy_candidates。
- 策略结果只读落库，用于历史分析和审计。
- 在适配层把策略引擎的 running 映射为 MES 的 in_progress，保持算法输入契约不变。

验收：告警去重，策略仿真可按 simulationId 查询。

### P4：灰度切换（2～3 天）

建议开关：

    PERSISTENCE_MODE=memory
    PERSISTENCE_MODE=shadow
    PERSISTENCE_MODE=read-db
    PERSISTENCE_MODE=database

切换顺序：

1. 主数据只读。
2. 订单查询。
3. 工单查询。
4. 报工事务。
5. 告警历史。
6. 策略历史。

每一步保留回滚开关，不在一次发布中切换全部模块。

## 9. 导入、校验和回滚

导入顺序：

    tenants
    -> factories
    -> production_lines
    -> devices
    -> production_orders
    -> work_orders
    -> work_order_reports
    -> work_order_status_history
    -> alarms
    -> strategy_runs / strategy_candidates

导入脚本必须支持：

- dry-run；
- 租户和外键校验；
- 数量和报工汇总校验；
- source_trace_id 重复检查；
- 导入统计和失败明细；
- 可重复执行。

回滚原则：

- 新列先 nullable，再补数据，最后改为 NOT NULL。
- 不直接删除旧列和历史数据。
- 数据库切换前保留 memory 模式。
- 以 work_order_reports 作为报工事实来源，订单和工单汇总数可重算校正。
- 发现汇总不一致时，停止切换，不删除数据。

## 10. 持久化测试契约

后续应将以下测试复制到 repository/integration 层：

1. 订单可创建绑定订单的工单。
2. 无效产线不能创建工单。
3. 跨租户订单不能创建工单。
4. completedQty 大于 plannedQty 被拒绝。
5. 报工合计不能超过计划数量。
6. goodQty + defectQty 必须等于 quantity。
7. 重复 sourceTraceId 不重复记账。
8. 暂停和取消没有原因时被拒绝。
9. 未完成计划数量时不能转为 completed。
10. 报工设备必须属于工单产线。
11. 并发报工最终完成数不超过计划数。
12. 租户 A 不能读取或修改租户 B 的订单、工单、报工和设备。

## 11. 本阶段结论

当前最稳妥方案：

- 本阶段只冻结 schema、约束、迁移顺序和测试契约。
- 不立即引入 Prisma，不改当前内存 MVP。
- 下一阶段先实现 P1 基础表和 Prisma Client 封装，再将 OrdersService、WorkOrdersService 改为可注入 repository。
- 业务服务依赖 repository 接口，不直接依赖 Prisma，允许 memory repository 与 PostgreSQL repository 并存。
- 报工是持久化切换的核心风险点，必须优先实现事务、幂等、行锁和审计链路。
